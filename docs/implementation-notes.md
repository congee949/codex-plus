# Implementation Notes

## Design Decisions
- **Matches Claude**: 768 / 960 / 1280 px content width, a segmented control, and Claude's wording. Sources: Claude's CSS `[data-transcript-width=s|m|l] → --max-content-width` and its settings definition `transcriptWidth`. Default is Narrow.
- **Suggestion provider**: `suggestion_provider()` in `codex_tw.py` resolves it on every request, and `provider()` in `SUGGESTION_MAIN` repeats the same order for the re-signed build. Without `tomllib` (Python < 3.11), `read_toml` reads tables and single-line strings only, which covers the provider keys. The order is described in [guide.md](guide.md#模型提供商).
- **Official build source**: the Sparkle appcast, read directly instead of through in-app Sparkle, because Sparkle refuses to update a locally signed host. The EdDSA key is pinned in the script.
- **Injection by stable anchors**: i18n ids plus structural regexes. React and SettingsRow aliases are taken by frequency. On 26.928.40906 SettingsRow was renamed `V`→`H` and the locator adapted without changes.
- **Pinned summary**: `thread-summary-panel-layout-*.js` decides gutter / shift / overlay from `(mainWidth - 736) / 2`. It now reads `globalThis.__ltwColumnWidth()`, which is content width + 2 × `--thread-body-inline-padding`, falling back to 736. Measured result: no overlap at any width with the sidebar shown or hidden. When there isn't room, as with Wide plus the sidebar shown on a 1868 px window, the app falls back to its native overlay popover.
- **Composer**: it already shares `--thread-content-max-width`. Measured: equal to the transcript width in a conversation and on the new-chat page.
- **Prompt suggestions**: Codex has no native equivalent. Its "Suggested prompts" (`settings.agent.ambientSuggestions`) only produce home-page task cards. Three parts:
  - The renderer CSP only allows OpenAI hosts and local providers usually send no CORS headers, so the HTTP runs outside the renderer: in the launcher through the `__lpsSend` binding (see [Launcher](#launcher)), or in a re-signed build through `SUGGESTION_MAIN`, an `ipcMain.handle` channel appended to `main-*.js` and exposed by `preload.js` as `window.__localPromptSuggestion`. Both forward only `GET /models` and `POST /responses` and reject senders outside `app://-/`. `bridge()` in `prompt-suggestion.js` uses whichever exists.
  - `prompt-suggestion.js` reads turns from `[data-turn-key]` and `[data-user-message-bubble]`. Assistant messages come from the parent of the screen-reader heading `[data-conversation-role=assistant]` ("ChatGPT said:"); the reply text skips that heading, the `aria-live` region that briefly announces "Response complete: …", and the `.turn-action-controls` timestamp row, so a finished turn keeps one signature. It treats a turn as finished after 1.5 s with no streaming markers. Because the turn list is virtualized, it only acts while the last rendered turn is on screen. The router is in-memory, so threads are keyed by `data-above-composer-conversation-id`. The app keeps threads you left mounted as inactive pages, so the thread ID, turns and composer are read only outside `[data-app-shell-active-page=false]`, `aria-hidden` and `inert`; each thread only ever shows its own suggestion. When a finished turn gets a suggestion is described in [Prompt suggestion rules](#prompt-suggestion-rules).
  - The suggestion text is swapped into the composer's own ProseMirror `.placeholder::before` through a CSS variable. Position, color and the hide-on-typing behavior all come from the native placeholder. Tab inserts the text with a synthetic `paste` event; `execCommand("insertText")` does not reach this editor.
- **Suggestion settings**: two rows go after `withComposerGroup:!1` in General → Composer. That anchor appears once in the Codex layout and once in the ChatGPT layout. Every control is one of the app's own components, found by frequency: Switch (`checked:`), the dropdown used by "Confirm before closing a window" and "Speed" (`align:\`end\`,triggerButton:` with `RadioGroup`), and the secondary toolbar button. The `ui` object is built lazily because those bindings are module-level lets initialized later. The rows share a chunk with Appearance, so the locator builds on top of that patch.

## Prompt suggestion rules
The rules follow Claude Code 2.1.283: `enr` and `h7r` decide whether to generate, `q` filters the output, and the SUGGESTION MODE prompt is reused with "Claude" replaced by "the assistant". Each finished turn is evaluated once (`decided`), so a turn skipped while the window was in the background stays skipped after refocusing.
- **Skipped before generating**, in this order (reason codes as in `__lpsStats`):
  - `unfocused`: `document.hasFocus()` is false or the page is hidden.
  - `early_conversation`: fewer than two assistant messages are rendered, counting `[data-conversation-role=assistant]` headings, so a first turn with several messages already qualifies. A thread that had history when it was opened never counts as early.
  - `pending_approval`: an approval card is open. The selector is the app's own `hasActiveApprovalSurface` test, `[data-codex-approval-surface]` outside inactive pages.
  - `unused_streak`: after 20 suggestions in a row were shown and not accepted, only every 10th eligible turn gets one. The count is kept in localStorage (`codex.local.prompt-suggestion.unused.v1`) and resets when one is accepted with Tab. A suggestion counts as unused when Esc dismisses it or a newer turn replaces it.
- **Not ported**: Claude's `last_response_error`, because Codex renders turn errors through a generic alert component without a stable attribute; `cache_cold`, because suggestions are a separate request without the main conversation's prompt cache; `plan_mode` and `rate_limit`, which have no page-side signal.
- **Output filter** (`rejectReason`): the first line, with wrapper tags, a `User:` prefix and surrounding quotes removed, must pass every check of `q`. Words are counted as in Claude: a space-separated word is 1 and a Han character 1/2, so the 12-word cap is about 24 Chinese characters. It rejects multiple sentences, formatting, labels, evaluations such as 谢谢 or 看起来不错, "no suggestion" text, and assistant-voice openings such as 我来 or Let me. One local change to `q`: one statement followed by one closing question, such as 好的。要苹果清单吗？, passes the sentence check when every quote and bracket is closed (`shortQuestion`).
- **Results that arrive late**: if the thread changed or the composer is no longer empty when the model answers, the result is dropped (`discarded`).
- **Context** (`buildContext`): only text rendered on the page. Turns are taken newest first, at most 6, until 8000 characters; the last turn is always kept. User messages keep their first 800 characters and assistant replies their last 1500, where options and questions usually are. When the first rendered turn is the thread's first turn (its virtualized slot has `top: 0`), its request is prepended as `Original request`.
- **Stats**: `globalThis.__lpsStats` keeps the last 50 outcomes per thread (`shown`, `accepted`, `dismissed`, `ignored`, `ready`, `discarded`, `error`, or a skip or filter reason), with the context size in characters. Each outcome is also sent through `__lpsSend` to the launcher, which writes one line to `logs/launcher.log` (`log_outcome` in `codex_launch.py`) with the thread, context size, and the candidate text or error, truncated to 200 characters.

## Launcher
`codex_launch.py` runs the official, unmodified bundle and adds the webview changes at runtime.
- **Debugging pipe, not port**: the app is spawned with `--remote-debugging-pipe`, so DevTools is reachable only on the launcher's fds 3/4. Electron's fuses (`EnableNodeCliInspectArguments` off) do not block this Chromium switch. A port would let any local process drive Codex.
- **Spawn**: `posix_spawn` with only stdio and the two pipe ends inherited, default signal handlers, and `responsibility_spawnattrs_setdisclaim`, so macOS privacy grants and prompts belong to ChatGPT rather than to Raycast or the shell.
- **Same locators**: `locate_changes(asar, runtime=True)` produces the webview part of the re-signed patch and skips main, preload and the peer helper. The result is cached in `runtime-cache/` per app.asar header, patch id and `ROUTES_VERSION`, because locating takes about 3 s.
- **Serving files**: `Target.setAutoAttach` with `waitForDebuggerOnStart` holds each new page until `Fetch.enable` covers the patched URLs. Existing files are replaced at the Response stage and keep the app's headers; files from `assets/` are fulfilled at the Request stage.
- **Head tags**: `app://` navigations from Electron's protocol handler never reach Fetch, so `index.html` cannot be replaced. `BOOTSTRAP`, a `Page.addScriptToEvaluateOnNewDocument` script, appends the CSS and module tags at `DOMContentLoaded`, which matches the end-of-`<head>` position of the HTML patch. The page's meta CSP allows them as `'self'`.
- **Binding**: the renderer restores `Runtime.addBinding` and new-document scripts after the initial process swap only while Runtime and Page are enabled, so both are enabled first. Each call checks `location.href` of the calling context before forwarding; the answer goes back through `Runtime.evaluate` of `__lpsResolve(id, ok, value)`.
- **Patch version**: the daemon loads the routes once at startup and records `codex_tw.patch_id()` in `launcher.json`. `launch` compares it with the current assets and offers a restart when they differ; `status` reports it as `patches_current`. Reloading the page does not pick up edits, because the served bytes stay in the daemon's memory.
- **Lifetime**: the launcher stays the app's parent. If it dies, ChatGPT keeps running with the already loaded patches, suggestion requests time out, and the next launch offers a restart.
- **Watch agent**: `watch` polls `ps` every 0.3 s. A new `/Applications/ChatGPT.app` process whose parent is not a launcher daemon gets SIGTERM and the launcher reopens the app; at that point it has no windows or state. Checking the parent covers the moment between spawn and the daemon writing `launcher.json`. Processes already running when the watcher starts are left alone.

## Tradeoffs
- The column width stays fixed when the pinned panel needs space, rather than shrinking to keep the panel pinned. This keeps native overlay semantics. Shrinking would need CSS tied to the panel state.
- Panel placement is recomputed only on main-width change or remount. Changing the width from Settings remounts the conversation, so this works in practice. A change synced from another open window refreshes on the next resize or navigation.
